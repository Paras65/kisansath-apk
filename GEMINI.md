# Antigravity AI Operational Rules — Kisan Saathi (फसल से लेकर बिक्री तक)

You are operating within a constrained compute environment for the **Kisan Saathi (किसान साथी: फसल से लेकर बिक्री तक)** application (PWA & Android TWA). To optimize resource usage, prevent quota drain, and ensure bulletproof reliability for farmers, you MUST strictly adhere to the following operational rules:

1. **Strict Scope:** Only address the exact agriculture-related problem, feature, or bug explicitly stated in the prompt. Do NOT perform unsolicited refactoring, unnecessary package additions, or tangential architectural overhauls.
2. **No Auto-Execution:** Never execute terminal commands (`npm`, `git`, build scripts, etc.), run background tasks, or perform destructive system actions without asking for explicit, in-line confirmation from the user first.
3. **Targeted File Access:** Do not scan or search the broader workspace unnecessarily. Restrict file system operations ONLY to the specific files explicitly mentioned, `@` tagged, or directly relevant to the user's immediate request.
4. **Concise Output:** Provide direct, clean answers and code snippets. Skip long-winded meta-explanations or boilerplate summaries unless explicitly requested.
5. **Stop on Failure:** If you fail to resolve an error or build failure after two attempts, stop immediately and ask for human clarification instead of repeatedly guessing, looping, or churning commands.
6. **Mandatory Feature & Advisory Documentation:** Whenever any new feature, calculator, scheme, or advisory tool is added, or an existing feature is modified/refactored, it MUST be immediately and synchronously documented in `docs/USER_MANUAL.md` (including updating the Table of Contents) before considering the task complete.
7. **Interrelated Feature Synchronization (Seed-to-Market Lifecycle Cohesion):** Because the platform covers the complete agricultural cycle (बुआई पूर्व → बुआई → पोषण → रोग निदान → कटाई → मंडी बिक्री), whenever any crop model, dosage formula, scheme rate (e.g. ₹3,100/क्विंटल धान उपार्जन), or data structure is modified or added, all interrelated upstream and downstream components (Fertilizer Calculator, Crop Doctor symptoms, Mandi rates, Farm Diary, and UI modals) MUST be audited and updated synchronously to prevent schema drift and broken farmer workflows.
8. **Farmer Data Security & Scalability Safeguards:** Every new or modified feature, calculator, or form MUST incorporate rigorous data validation, input sanitization, bounded collection limits (e.g., Farm Diary entries, direct buyer listings), and leak-free memory handling to ensure absolute data integrity and high-load resilience on low-end smartphones.
9. **Public Dashboard & Lifecycle Journey Synchronization:** Whenever any new feature, module, or core agricultural capability is added, refactored, or updated, the main dashboard (`HomeTab` lifecycle stepper, daily weather advisory, quick action tools, and navigation links) MUST be synchronously audited and updated to accurately reflect the functionality and stay 100% aligned with `docs/USER_MANUAL.md`.
10. **Offline-First, Minimal Data Fetching & Sensitive Data Protection:** Network requests must only trigger where strictly necessary, backed by offline caching (`sw.js`). Never eagerly fetch or expose sensitive farmer records (Aadhaar numbers, bank account/DBT details, land registry numbers, or PINs) in unencrypted storage or network logs. Project only the minimal required fields for the UI.
11. **User Manual Non-Technical Policy (Farmer-Centric):** `docs/USER_MANUAL.md` is strictly an end-user guide for farmers, agricultural extension workers (RAEO), and cooperative societies (समितियां). For application security, attack surface reduction, and clarity, it MUST NOT contain internal technical implementation details, backend route signatures (e.g., `/api/...`), database query logic, cryptographic internals, or code paths. All manual content must be described strictly from an operational, practical, and farmer-friendly perspective (हिंदी/सरल भाषा में).
12. **Eliminate Code Redundancy & Enforce DRY Architecture:** Never duplicate calculation logic (e.g. N:P:K dosage formulas, MSP bonus calculations, Web Speech voice readouts) across multiple tabs or views. Shared operational workflows (such as speech synthesis, unit conversions, offline sync, and storage handling) MUST always be encapsulated within centralized, typed service modules (e.g., `src/utils/...`, `src/services/...`, `src/data/...`) as a single source of truth.
13. **Enterprise PWA Security, Zero-PII Offline Policy & Standards:** Every new feature, route, or bug fix MUST strictly uphold web and mobile application security standards (OWASP / ISO 27001): (a) Service Worker (`sw.js`) and Cache Storage must NEVER store authenticated API responses, farmer PII, or sensitive financial records; (b) Direct buyer contact forms must validate phone numbers and sanitize inputs against XSS; (c) Client session data must be actively purged on logout or reset.
14. **Dual PWA & Android TWA / APK Harmony (Zero-Conflict Policy):** The platform operates concurrently as a Progressive Web App (PWA) and a native Android Trusted Web Activity (TWA / APK package `in.co.init65.kisan`): (a) **Platform-Aware Adaptation:** In standalone/TWA mode, suppress redundant web install banners, handle Android hardware back-button navigation with modal stack unwinding, apply native status bar theming (`#1b5e20`), and handle offline states gracefully; on Web/PWA, preserve seamless browser fallbacks, standard PWA installation prompts, and public APK download guides; (b) **Zero Feature Degradation:** Android enhancements must NEVER break desktop or mobile browser workflows, and Web improvements must NEVER cause layout shifts or crashes in Android WebView; (c) **Synchronous Version Alignment:** Version numbers across `package.json`, `manifest.json`, `twa/twa-manifest.json`, and `docs/USER_MANUAL.md` MUST remain 100% synchronized.
15. **Environment-Driven Configuration & Canonical Origin Integrity (Zero-Hardcoding):** All external agricultural portal links (Agri-Stack, Bhuiyan, CG Khadya, CREDA, PM-Kisan) and future API endpoints MUST be centralized in configuration files (e.g. `.env` or dedicated config modules) with no hardcoded domain literals scattered across the code. Ensure proper canonical address resolution whether accessed via browser URL or Android WebView / TWA.
16. **Synchronous Release, Tagging & Build Verification Protocol (Mandatory Automated Tagging):** Whenever updating or releasing new builds, version bumps across ALL 8 targets (`package.json`, `public/version.json`, `public/manifest.json`, `twa/twa-manifest.json`, `.env`, `src/config/appConfig.js`, `server/routes/api.js`, and `docs/USER_MANUAL.md`) must follow strict release discipline:
    (a) **Strict 8-Target Version Alignment:** Version numbers and Android `appVersionCode` across all 8 files (`package.json`, `public/version.json`, `public/manifest.json`, `twa/twa-manifest.json`, `appConfig.js`, `.env`, `server/routes/api.js`, and `docs/USER_MANUAL.md`) MUST be updated synchronously before every commit;
    (b) **Clean Build Verification:** Verify clean build via `npm run build` with zero errors before committing or tagging;
    (c) **Automatic Annotated Git Tagging (Zero-Prompt Policy):** The assistant MUST automatically create an annotated semantic Git tag matching the format `v<version>` (e.g., `git tag -a v1.0.11 -m "Release v1.0.11 - <features>"`) and push with tags (`git push origin main --tags` and `git push public-apk main --tags`) on every release. NEVER wait for or force the user to remind you to tag;
    (d) **Release Notes & In-App Update Engine:** `public/version.json` and `server/routes/api.js` release notes must be updated synchronously to ensure the in-app update engine immediately detects the new version;
    (e) **Realistic Offline Scope:** Never embed bloated static datasets (e.g. offline pincode maps) for features that inherently require network connectivity (such as new farmer registration).
